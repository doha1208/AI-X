# 실시간 시간대 반영 안심 귀갓길 내비게이션

## Problem Statement

이사 온 지 얼마 안 됐거나 여행 중이라 지역 지리에 익숙하지 않은 사람은 어느 길이 위험한지 판단할 근거가 없다. 기존 지도/내비게이션 앱(카카오맵, 네이버지도 등)은 최단시간·대중교통 경로만 안내하며, 안전이라는 축을 아예 고려하지 않는다. 안심이앱·안심in 등 지자체 서비스는 CCTV/비상벨 "위치 표시"에 그치고 목적지까지의 "경로 추천"을 하지 않는다.

## Evidence

- 안심 귀갓길 관련 공공데이터(서울시 안심귀갓길 안전시설물)가 이미 존재함 — 문제 해결에 쓸 수 있는 재료가 있다는 방증. [data.go.kr](https://www.data.go.kr/data/15112100/fileData.do?recommendDataYn=Y)
- 서울시가 "안심이앱" 기능을 계속 강화 중이라는 것은 지자체 차원에서 귀갓길 불안이 실제 대응 대상 문제임을 시사. [경향신문](https://www.khan.co.kr/article/202309041454001)
- Assumption — "시간대를 반영한 실시간 안전 내비게이션"에 대한 실제 사용자 수요(정량 데이터)는 검증되지 않음. 학기말 발표/시연으로 개념 검증 예정.

## Proposed Solution

기존 `safety_weighted` 경로 탐색 엔진(OSM 그래프 + 동별 안전점수 비용 가중치, `backend/app/services/safe_route.py`에 이미 구현됨)을 두 축으로 확장한다:
1. **시간대 인식**: 안전점수 계산에 주간/야간 시간대를 반영 — 같은 길이라도 밤에는 안전점수가 낮아지도록.
2. **실시간 재경로**: 사용자가 이동하는 동안 위치가 일정 거리/시간 이상 벗어나면 서버에 재요청해 경로를 갱신하는 폴링 기반 라이브 내비게이션.

여기에 범죄 발생 지점, 야간 순찰 범위, 도움 요청 가능 장소(편의점·파출소 등)를 점(point) 단위 데이터로 추가해 안전점수 계산과 지도 표시에 반영한다(스코프는 possible/optional, 아래 MoSCoW 참고).

## Key Hypothesis

우리는 시간대를 반영한 실시간 안전 경로 추천이 지역에 익숙하지 않은 사람들의 야간 이동 불안을 해소해줄 것이라 믿는다.
우리는 우리 서비스가 추천하는 야간 경로의 평균 안전점수가 기존 지도 앱의 최단경로 대비 유의미하게 높을 때(목표 수치 TBD — 검증 필요) 맞다는 것을 알게 될 것이다.

## What We're NOT Building

- **백그라운드 GPS 추적 / 네이티브 앱** — 웹 기반 폴링으로 충분히 데모 가능하다고 판단. 브라우저 탭이 꺼지면 추적도 끊기는 제약은 감수.
- **SOS/긴급신고 연동** — 안심이앱이 이미 하는 영역이며, 학기 프로젝트 범위를 벗어남.
- **다중 사용자 동시 접속 성능 최적화** — 시연/평가 규모에서는 불필요. 프로덕션급 트래픽 대비는 범위 밖.

(추가 out-of-scope 항목은 기능 구현을 제안할 때마다 사용자가 즉시 판단 — 고정 목록이 아니라 진행형 결정)

## Users & Context

**Primary User**
- **Who**: 최근 이사했거나 여행 중이라 목적지 주변 지리에 익숙하지 않은 사람
- **Current behavior**: 카카오맵/네이버지도로 최단경로를 그대로 따라가거나, 지인에게 안전한 길을 물어봄
- **Trigger**: 밤늦게 낯선 동네를 혼자 이동해야 하는 상황
- **Success state**: 목적지까지 이동하는 동안, 시간대와 실시간 위치를 반영한 안전 경로를 계속 안내받아 위험한 길을 피해감

**Job to Be Done**
When 밤에 익숙하지 않은 동네를 혼자 이동해야 할 때, I want to 지금 시간대 기준으로 가장 안전한 길을 실시간으로 안내받고 싶다, so I can 위험한 골목을 모른 채로 지나가는 상황을 피할 수 있다.

**Non-Users**
평소 다니는 익숙한 동네만 이동하는 사람, 자차/택시 등 도보 이동이 아닌 경우는 이 기능의 대상이 아님.

## Solution Detail

### Core Capabilities (MoSCoW)

| Priority | Capability | Rationale |
|----------|------------|-----------|
| Must | 시간대(주간/야간) 반영 안전점수 계산 | 교수님이 지목한 핵심 평가 포인트, 현재 완전 부재 |
| Must | 실시간 위치 갱신 기반 재경로 계산(폴링) | 핵심 가설(b)이자 요청한 최소 기능 |
| Should | 범죄 발생 지점 데이터를 안전점수에 반영 | 교수님 예시 언급, 데이터 확보 여부에 따라 난이도 유동적 |
| Should | 야간 순찰 범위 표시/반영 | 교수님 예시 언급, 공공데이터 존재 여부 확인 필요 |
| Should | 도움 요청 가능 장소(편의점/파출소) 지도 표시 | 교수님 예시 언급, 표시만이면 Must에 준하는 난이도 |
| Could | 재경로 시 이전 경로를 유지하며 백그라운드 갱신(낙관적 UI) | 체감 지연을 줄이는 UX 개선, 없어도 기능은 동작 |
| Won't | 백그라운드 GPS 추적, SOS 연동, 다중 사용자 성능 최적화 | Out of Scope 참고 |

### MVP Scope

시간대(주/야간) 반영 안전점수 + 실시간 폴링 기반 재경로. 이 둘이 있어야 "실시간으로 시간을 고려한 귀갓길 추천"이라는 교수님 요청의 핵심이 성립한다.

### User Flow

1. 사용자가 출발지/도착지 설정 → 현재 시각 기준 안전 가중 경로 수신 (기존 `POST /safety/route` 확장)
2. 이동 시작 → 프론트엔드가 일정 주기/거리마다 현재 위치를 서버로 전송
3. 서버가 임계값 초과 시에만 재계산해 새 경로 반환, 지도 갱신
4. (Should) 지도 위에 범죄지점/순찰범위/도움장소 마커 표시

## Technical Approach

**Feasibility**: MEDIUM — 라우팅 엔진은 이미 존재(`find_safe_routes`), 신규 구축이 아니라 확장. 신규 데이터 수집과 폴링 아키텍처가 리스크.

**Architecture Notes**
- `app/services/safety_score.py`의 `compute_safety_scores`는 현재 정적 가중치(CCTV 40%/보안등 20%/범죄역수 40%) — 시간대 팩터를 추가하려면 동일 동(dong)이라도 시간대별로 다른 점수를 낼 수 있는 구조로 확장 필요 (예: 야간엔 CCTV/보안등 가중치를 낮추고 범죄 가중치를 높이는 등, 또는 시간대별 별도 컬럼)
- `app/services/safe_route.py:_assign_edge_costs`가 매 요청마다 전체 edge를 순회 — 실시간 폴링을 붙이면 이 비용이 반복 호출됨. 재계산 트리거를 "일정 거리 이상 이동 시"로 제한해 서버 부하를 통제해야 함
- `app/api/safety.py`의 `POST /safety/route`는 1회성 — 라이브 갱신을 위한 새 엔드포인트(예: 위치 업데이트를 받아 조건부로 재계산 결과를 반환) 또는 기존 엔드포인트 재사용 + 프론트 폴링 로직으로 해결 가능. 아키텍처 결정은 구현 단계에서.
- `SafetyZone`(app/models/safety_zone.py)은 동 단위 집계 모델 — 범죄지점/순찰범위/도움장소는 점 단위이므로 별도 테이블/모델이 필요할 가능성 높음

**Technical Risks**

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| 범죄지점/순찰범위/도움장소 공공데이터가 동 단위 집계 수준으로만 존재하고 점 단위로는 없을 수 있음 | M | 조사 우선 수행, 없으면 해당 Should 항목은 스코프에서 제외 |
| 폴링 재계산이 서버 응답 지연을 유발 | M | 거리/시간 임계값 기반 재계산 제한, 필요시 벤치마크 후 조정 |
| 학기말(13~14주차)까지 완성 압박 — 10주 남짓 | M | Must 항목(시간대+실시간)을 먼저 완성하고 Should는 여유가 있을 때 추가 |

### Phase Details

**Phase 1: 시간대 반영 안전점수**
- **Goal**: 동일 지역이라도 요청 시각(또는 사용자가 선택한 시간대)에 따라 다른 안전점수가 나오게 한다
- **Scope**: `compute_safety_scores` 확장 또는 시간대별 가중치 함수 추가, `find_safe_routes` 호출 시 현재 시각 전달
- **Success signal**: 같은 출발/도착지에 대해 주간 요청과 야간 요청의 추천 경로 또는 안전점수가 달라짐

**Phase 2: 실시간 재경로 API/폴링**
- **Goal**: 이동 중 위치가 바뀌면 경로가 갱신된다
- **Scope**: 위치 업데이트 수신 엔드포인트(또는 기존 엔드포인트 재사용), 재계산 임계값 로직, 프론트엔드 폴링/지도 갱신
- **Success signal**: 데모에서 위치를 이동시켰을 때 경로가 실제로 바뀌는 것을 화면으로 확인 가능

**Phase 3: 점 단위 안전 데이터 조사**
- **Goal**: 범죄지점/순찰범위/도움장소 데이터의 실존 여부와 형태를 확인
- **Scope**: 공공데이터포털 검색, 데이터 형식(좌표 단위/공개 범위) 확인
- **Success signal**: "쓸 수 있음" 또는 "이번 학기엔 불가능" 중 하나로 결론 확정

**Phase 4: 점 단위 데이터 반영**
- **Goal**: 확보된 데이터를 안전점수 계산 또는 지도 표시에 반영
- **Scope**: Phase 3 결과에 따라 유동적 — 신규 모델/ingest 스크립트/점수 반영 로직
- **Success signal**: 지도에서 해당 데이터가 실제로 보이거나 경로 계산에 영향을 줌

**Phase 5: 지도 시각화**
- **Goal**: 실시간 경로 갱신과 추가 안전 정보를 사용자가 눈으로 확인 가능하게
- **Scope**: `frontend/src/components/SafetyMap.tsx` 확장
- **Success signal**: 발표 시연에서 실시간 재경로 + (가능하면) 추가 마커가 자연스럽게 보임

### Parallelism Notes

Phase 3(데이터 조사)은 순수 리서치라 Phase 1, 2와 동시에 진행 가능 — 코드 변경과 무관. Phase 4는 3의 결론이 나와야 스코프가 확정되므로 순차.
